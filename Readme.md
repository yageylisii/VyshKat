# ВышКат

Консольное приложение для учёта парка прокатной техники и инвентаря. Оно принимает транспорт и вещи после техосмотра, выдаёт транспорт в аренду и показывает количество предметов, суммарный суточный расход энергии и доступную новичкам технику. Данные хранятся в памяти и исчезают после завершения программы.

## Запуск

Нужен .NET SDK 10. Из корня проекта:

```bash
dotnet run
```

В меню: `1` — добавить транспорт или вещь, `2` — арендовать транспорт, `3` — показать статистику, `0` — выйти.

При добавлении каждого предмета указывают инвентарный номер и состояние. Транспорт принимает состояние от 1 до 100, вещи — от 0 до 100. `ServiceCenter` пропускает предмет в парк при состоянии от 70. Инвентарные номера не должны повторяться.

**Простота для новичка есть только у транспорта.** Это отдельная характеристика от 1 до 10: при значении от 6 свободный транспорт можно выдать новичку. У вещей (шлема, док-станции и зарядного шкафа) такой характеристики нет; для них проверяется только состояние при приёме в парк.

Тесты находятся в отдельном проекте на xUnit:

```bash
dotnet test tests/VyshKat.Tests.csproj
```

## Устройство проекта

- `core/Vehicles` и `core/Equipment` — транспорт и вещи с их свойствами и правилами.
- `core/Interfaces` — договоры для хранилища (`IPark`), техосмотра (`IServiceCenter`), инвентарного объекта (`IInventoryItem`), потребителя энергии и создателей предметов.
- `core/Memory/Park.cs` — хранение объектов в памяти и проверка уникальности инвентарных номеров.
- `core/Services` — приём транспорта и вещей, техосмотр и аренда; `core/Staticstics.cs` — расчёт статистики.
- `app/ServiceRun.cs` — команды консольного приложения; `src/Input.cs` и `src/Output.cs` — ввод и вывод.
- `app/Creators` — создатели всех пяти видов транспорта и вещей: каждый реализует `IItemCreator`, читает нужные данные и возвращает предмет.
- `app/Main.cs` — настройка DI-контейнера и запуск приложения. Один `Park` зарегистрирован как `Singleton`, поэтому все сервисы работают с одним парком.

## SOLID: что применено наиболее явно

### D — принцип инверсии зависимостей (DIP)

Наиболее явно виден **DIP — принцип инверсии зависимостей**. `ParkService` получает `IPark` и `IServiceCenter` через конструктор, а `RentalService` и `StatisticsService` получают `IPark`. Сервисы не создают хранилище и техосмотр внутри себя. В `app/Main.cs` DI-контейнер связывает `IPark` с `Park`, а `IServiceCenter` с `ServiceCenter`. Поэтому реализацию техосмотра можно заменить при сборке приложения или теста, не меняя код `ParkService`.

### S — принцип единственной ответственности (SRP)

Также используется разделение ответственности: `ServiceCenter` проверяет состояние предмета; `ParkService` добавляет прошедший проверку предмет в парк; `Park` хранит предметы; `RentalService` проверяет возможность аренды; `ServiceRun` управляет командами, а не хранит предметы самостоятельно. Код разложен по папкам в соответствии с ролями: модели и правила предметной области находятся в `core`, создатели и запуск приложения — в `app`, консольный ввод и вывод — в `src`, проверки поведения — в `tests`.

### O — принцип открытости/закрытости (OCP)

Каждый вид имеет свой класс в `app/Creators`, реализующий `IItemCreator`. Он задаёт код и название для меню, читает нужные данные и возвращает объект через `Create()`. `ServiceRun` получает все реализации через конструктор, ищет подходящую по `Code` и вызывает её `Create()`. `Output` строит список типов из тех же реализаций.

Например, чтобы добавить ещё один вид транспорта, нужно создать его класс и новый `IItemCreator`, а затем зарегистрировать создатель в `Main`:

```csharp
services.AddTransient<IItemCreator, NewVehicleCreator>();
```

Для нового вида `Vehicle` или `EquipmentItem` код выбора в `ServiceRun` и список пунктов в `Output` менять не требуется. Регистрация в `Main` остаётся местом, где приложение собирается из реализаций.

## Сознательное ограничение

**Граница применения OCP:** при появлении принципиально новой категории предметов придётся расширить `ServiceRun.AddCreatedItem()`, где сейчас различаются `Vehicle` и `EquipmentItem`. Для текущей задачи, в которой есть только транспорт и оборудование, это ограничение приемлемо.

Часть поведения расширяется без изменений статистики: новый класс, реализующий `IEnergyConsumer`, попадёт в расчёт суммарного расхода энергии; новый класс транспорта, наследующий `Vehicle`, будет найден парком как транспорт.

## Что произойдёт при расширении

- **Новый вид транспорта или оборудования.** Понадобятся новый класс, наследующий `Vehicle` или `EquipmentItem`, и реализация `IItemCreator` с уникальным кодом команды. После регистрации создателя в `Main` он появится в меню без изменения `ServiceRun`. Хранение через `IPark` и подсчёт всех предметов продолжат работать с ним без отдельной ветки. Для транспорта также работают поиск и аренда. Если предмет потребляет энергию, он должен реализовать `IEnergyConsumer`.
- **Сотрудники.** Сейчас парк хранит только инвентарные объекты. Для сотрудников потребуются своя модель, способ хранения и команды. Добавлять сотрудника в `IInventoryItem` только ради повторного использования `Park` не стоит: у сотрудника нет инвентарного номера вещи. Текущие правила аренды транспорта от этого не меняются, пока требования не связывают аренду с сотрудниками.
- **Склад запчастей.** Ему понадобятся модели запчастей, учёт количества и операции поступления/расхода. Если склад ведётся отдельно от прокатного парка, его можно добавить отдельным сервисом и хранилищем. Существующую аренду менять не потребуется, пока запчасти не участвуют в её правилах.

## Тесты и подмена техосмотра

`tests/ParkServiceTests.cs` содержит тесты `AddsAcceptedVehicle` и `SkipsRejectedVehicle`. В них `FakeServiceCenter` реализует `IServiceCenter` и заранее возвращает `true` или `false`. Тест регистрирует эту подмену в DI-контейнере вместо настоящего `ServiceCenter`, запрашивает `ParkService` и проверяет, появился ли транспорт в общем `Park`.

Тест `RequiresConditionAtLeast70` использует настоящий `ServiceCenter` и проверяет границу для транспорта: состояние `69` отклоняется, `70` принимается. `ChecksEquipmentCondition` проверяет ту же границу для шлема. Правило для новичков проверяют тесты `RejectsDifficultVehicleForBeginner` и `RentsSuitableVehicleOnce` в `tests/RentalServiceTests.cs`: транспорт с простотой `5` новичку не выдаётся, а с простотой `6` выдаётся только один раз. `tests/StatisticsServiceTests.cs` дополнительно проверяет, что в список для новичков попадает только подходящий и ещё не арендованный транспорт.
